# Plan 147 — Exhaustive application coverage

Status: `route-inventory-in-progress`

This is the route-by-route coverage contract for the whole Ossie application.
It exists because grouped surface cards are useful summaries, but they are not
proof that every shipped page, section, or state has been reviewed.

## What “whole application” means here

Every shipped browser-visible route and route variant is listed below. Each
entry must eventually have:

- an exact path shape and owning page/boundary;
- every page-owned section and meaningful interactive state identified;
- focused tests for behavior and state transitions;
- desktop, narrow/reflow, keyboard, reduced-motion, and native-zoom evidence
  where the state can be exercised safely;
- loading, empty, populated, error/retry, denied/read-only, archived/frozen,
  validation, unsaved/saving, destructive, and long-content coverage where
  applicable;
- two independent agent inputs for each meaningful implementation slice; and
- a final human decision in the persistent review dashboard.

Grouped Plan 147 surface records remain useful evidence, but a grouped record
does not close an individual route below by itself. `Grouped evidence` means
the route has been touched by a family-level pass and still needs this exact
route/state reconciliation. `Component evidence` means the owning component
has focused tests but does not claim browser proof. `Blocked` is reserved for
an external capability or fixture that cannot be truthfully exercised in the
current environment.

## State and viewport matrix

The pass will mark an item `verified` only when the applicable cells have a
truthful test or browser evidence link. A component test is not silently
counted as browser evidence.

| Dimension     | Required cells                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Data          | loading, empty, populated, long content/labels, slow request, failed request, pagination/filter transition                                                          |
| Permissions   | owner/admin/editor/viewer, unauthenticated, forbidden, archived/final/frozen, owner-only controls hidden, public-link boundary                                      |
| Mutation      | idle, validation failure, unsaved, saving/disabled, success confirmation, conflict/stale data, retryable failure, destructive confirmation/failure                  |
| Public access | exact link, canonical redirect, password challenge, incorrect password, unavailable, internal-only, revoked, expired, unknown, embed, no metadata leakage           |
| Layout        | desktop 1440/1280, narrow 390/360, compact extension 180, 320 where shell applies, native browser zoom 200% where available                                         |
| Interaction   | keyboard focus order, skip link/main focus, tab through controls, enter/space activation, direct manipulation where applicable, reduced-motion preference           |
| Engineering   | no console errors, no failed requests except expected boundaries, no horizontal overflow, axe results, typecheck/lint/build, focused tests, two independent reviews |

## Current truth and next gate

This inventory is intentionally not marked complete yet. The existing Plan 147
bundle has strong grouped coverage across these route families and broad
component tests, but it also records real limits: missing populated browser
fixtures for some public/internal paths, the installed extension-toolbar click,
native 200% coverage outside bounded samples, known contrast-background probes,
and the Project workspace route-ownership reconciliation. Those remain open
until this inventory links exact route/state evidence or a truthful blocker.

The current engineering baseline is green: the web suite ran on 2026-08-08
with 95 test files and 551 tests passing. All 39 route-owned page types have a
focused page or boundary test, and `apps/web/src/lib/routes.test.ts` exercises
the canonical, legacy, public, embed, and unsupported path parsing. That is a
behavior baseline, not a claim that all 39 routes have independent browser
screenshots. The nested section audit still has a small set of owners covered
through parent tests rather than direct tests: `CaptureSessionDetailShell`,
`GuideEditorWorkbench`, `InteractiveDemoEditorShell`,
`InteractiveDemoReadOnlyPage`, and `InteractiveDemoWorkbench`; lazy wrapper
fallbacks are covered through App/boundary paths. These are explicit review
targets, not silently treated as complete.

The next engineering gate is therefore:

1. reconcile every row against current App routing and the existing ledger;
2. identify uncovered individual routes, sections, and states rather than
   assuming family evidence covers them;
3. implement missing UI/state behavior test-first;
4. run two independent reviews for each meaningful slice;
5. refresh this file, the ledger, and the HTML dashboard with exact links; and
6. only then hand the complete application to the user for the one final human
   review.

The final human review remains a separate gate. Agent acceptance, grouped
screenshots, or this inventory alone must never be reported as human approval.
